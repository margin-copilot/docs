### Cross-report reconciliation
- T-SQL RLS "applies to all users incl. dbo" (B3) holds on Warehouse and on a SQL analytics endpoint in **delegated mode**. In **user identity mode** the endpoint ignores T-SQL RLS and uses OneLake roles (C2). Pick one mode up front; switching deletes SQL roles.
- Data Agent per-user RLS from Python (B3e) and custom SQL tool (C2) both need the OBO flow in C1; the SQL path is documented end to end, the Data Agent path is inference.

3. **Policy RAG:** AI Search Free, push API, GA group-ID security filter; native ACL filter as stretch.
4. **Identity:** SPA + API app registrations, `OnBehalfOfCredential` with Container App managed identity as federated credential. Test users are workspace Viewers only.
5. **Evals:** `azure-ai-evaluation` + MAF `LocalEvaluator` in GitHub Actions (OIDC login for judge model); local red-team scan [PREVIEW].
6. **Copilot Studio:** drop from core; optional build-only demo in the trial test pane.

### A2. Python agent options

### A3. Recommendation (agent's)
**MAF self-hosted on Azure Container Apps, `FoundryChatClient` against the Foundry project, `HandoffBuilder` with a triage agent as start agent.**

```python
@tool(approval_mode="always_require")
def submit_proposal(proposal_id: str) -> str: ...
wf = HandoffBuilder(name="router", participants=[triage, data, policy, action],
                    checkpoint_storage=storage).with_start_agent(triage).build()
# request_info with function_approval_request -> save the request, return 202
# approval arrives later:
# wf.run(checkpoint_id=cid, responses={rid: req.data.to_function_approval_response(approved=True)})
```

- Why: only GA option covering handoff routing + approval with checkpoint/resume [13], OTel to App Insights with token counts (`gen_ai.usage.input_tokens` / `output_tokens`, `gen_ai.client.token.usage`) [15], `evaluate_agent()` for CI [16], and portable to Foundry hosted agents later.
- Write SQL tool and Search tool as own function tools (Search: `azure-search-documents`, hybrid + semantic ranker, return citations). Foundry built-in AI Search / Fabric tools have "limited support" in agent evaluators [21].
- Trade-offs:
  - Handoff is interactive: no handoff returns control to user. If orchestrator should keep control, agents-as-tools is simpler [13].
  - On ACA the service is an "external agent": Foundry portal traces [PREVIEW] [3] (App Insights works normally). Cloud red teaming for agent risks only supports Foundry-hosted agents [23].
  - `FileCheckpointStorage` writes local files; ACA needs Azure Files mount or custom store (inference).
  - No built-in cost field: tokens × own price table.
- Preview / could break: Foundry Workflows retire 2026-12-01; Handoff "autonomous mode" experimental [13]; MAF Foundry observability + eval integrations preview at 1.0 [11]; client-side GenAI tracing in `azure-ai-projects` "experimental preview" [26]; MAF releases ~weekly, min Python raised to 3.11 in 1.25.0, so pin versions [25].

## C. Entra OBO and per-user data access

"Inference" = agent's reasoning, not stated by a source.

### C1. OBO in Python
- Packages: `msal` 1.39.0 (2026-09-17) [S4]; `azure-identity` 1.27.0 (2026-10-26) [S5].
- MSAL `ConfidentialClientApplication.acquire_token_on_behalf_of(user_assertion, scopes, claims_challenge=None)` [S2]. Posts straight to token endpoint, no cache lookup [S3], so cache yourself (e.g. hash(assertion)+scope). Learn sample's in-memory cache "should not be used for production" [S8].
- `OnBehalfOfCredential(tenant_id, client_id, client_secret= | client_certificate= | client_assertion_func=, user_assertion=)` [S6]. 1.27.0 keys cache by assertion; fixes 1.26.0 async regression and an earlier wrong-account cached-token bug [S5].
- Recommendation (agent's, no source preference): `OnBehalfOfCredential`, one instance per request. Plugs into Azure SDK clients and mssql-python `token_provider=`.
- API app client credential, best first: (1) user-assigned managed identity as federated credential (same tenant, audience `api://AzureADTokenExchange`, max 20 federated creds per app) [S7]; (2) certificate (PFX path, SHA-256 thumbprint) [S2]; (3) client secret. Apps with custom signing keys can't be OBO middle tier [S1].
- App registration: API exposes `api://<id>/access_as_user`; pre-authorize front-end client or use `knownClientApplications` + `.default` for combined consent [S1]. Don't mix `.default` with other delegated scopes (`AADSTS70011`) [S1]. Incoming token `aud` must be your API (can't OBO a Graph token) [S1]. `OnBehalfOfCredential` needs admin consent for delegated permissions [S6].

```python
cred = OnBehalfOfCredential(TENANT, API_CLIENT_ID, user_assertion=incoming_jwt,
    client_assertion_func=lambda: mi.get_token("api://AzureADTokenExchange/.default").token)
```

### C2. Fabric Warehouse / Lakehouse SQL analytics endpoint
- TDS port 1433, Entra users/SPs only; no SQL auth, no MARS. Always set Database: since May 2026 omitting it connects to `master` [S9]. Drivers: ODBC, JDBC, OLE DB, SqlClient [S10].
- pyodbc + ODBC Driver 18: token via `SQL_COPT_SS_ACCESS_TOKEN` (1256), 4-byte length + UTF-16LE-expanded token; no `UID`/`PWD`/`Authentication` in connection string [S12].
- **Linux unixODBC pooling ignores the token: pooled connection can be reused under the previous user's identity.** Set `Pooling=No` in odbcinst.ini, don't enable app pooling [S12]. (`pyodbc.pooling=False` is agent's addition, unchecked.)
- `mssql-python` 1.17.0 (2026-11-02, GA, Python 3.10+) [S13]: `attrs_before={1256: packed_token}` and `token_provider=<credential>`. `token_provider` pools keyed on token; no token refresh on live connection [S14]. Wiki doesn't name the connect function taking `token_provider`: verify [S14].
- Token scope: `https://database.windows.net//user_impersonation` (double slash), per Fabric WDK OBO steps; API app needs "Azure SQL Database" delegated `user_impersonation` [S11]. [UNCERTAIN] some community examples use Power BI audience; no official doc.
- T-SQL RLS (`CREATE SECURITY POLICY`, filter predicates) supported on Warehouse and SQL analytics endpoint (endpoint: function + policy OK, no tables). Applies to all users incl. dbo [S15].
- **SQL analytics endpoint access modes** [S16]:
  - Delegated mode (default for new endpoints): T-SQL RLS works; storage read as item owner.
  - User identity mode: OneLake roles govern reads, **T-SQL RLS ignored**.
  - Switching modes cancels running queries workspace-wide and deletes TVFs and SQL roles.
- OneLake security RLS/CLS via SQL endpoint in user identity mode: GA [S17].
- OneLake RLS limits [S16]: single-expression rules per table (no dynamic/multi-table RLS); role changes sync up to 5 min; applies even to Admin/Member/Contributor; users need item Read to connect; no mail-enabled groups; Warehouse T-SQL security doesn't carry through shortcuts.

### C3. Power BI semantic model RLS
- **executeQueries (JSON)** [S19]: delegated scope `Dataset.Read.All`, resource `https://analysis.windows.net/powerbi/api/.default` [S22]. User needs Read + Build. Tenant setting "Semantic Model Execute Queries REST API" on [S19][S25]. Limits: 1 query + 1 table per call, 100k rows / 1M values, 15 MB, 120 req/min/user. Service principals not supported for RLS/SSO models.
- **RLS applies to delegated user only if Viewer.** Admin/Member/Contributor bypass it, even when Viewers also have Build [S23]. Users in no role see no data. Entra security groups work as role members; M365 groups don't [S23].
- **executeDaxQueries (Arrow)** [S20][S21]: no fixed row cap; needs Premium/Fabric capacity + XMLA tenant setting; `effectiveUsername` only for workspace admins; Pro/PPU callers 40 req/min. [UNCERTAIN] setting location: Integration settings [S19][S20][S25] vs Developer settings [S21].
- XMLA: read-only on by default for capacities; needs Build; RLS honored for Build users; SPs can't be RLS members [S24]. [UNCERTAIN] page never names F2 or Python clients: stick to REST.

### C4. Azure AI Search document-level security
- Security filters (own string filter on group IDs): GA, any API version [S26].
- Native Entra ACL/RBAC permission filters: [PREVIEW] [S26]. Purview sensitivity labels, SharePoint ACLs: [PREVIEW] [S26].
- Native setup: index `permissionFilterOption: "enabled"` + filterable fields with `permissionFilter: userIds | groupIds | rbacScope`. Entra object IDs, max 1000 per field, one field per type; special values `"all"`/`"none"`. **Push API ingestion works**; portal doesn't support the feature [S28].
- Indexers ingesting permissions: ADLS Gen2 (ACLs + RBAC), Blob (container RBAC), SharePoint [S26].
- Query: `Authorization` = app token (Search Index Data Reader); `x-ms-query-source-authorization` = user's raw token, no "Bearer", via OBO for `https://search.azure.com/.default` [S27][S29]. Groups resolved via Graph; evaluation failure returns 5xx, not partial results. No user token: ACL docs not returned [S27]. Pushed ACLs change only on re-ingest [S27].
- API versions: Learn lists 2026-08-01-preview (latest preview), 2026-04-01 (latest stable) [S30]. **[UNCERTAIN] possibly GA now:** `azure-search-documents` 12.1.0 (2026-11-13) targets "2026-10-01 GA API" with `PermissionFilter`, `permission_filter_option`, `query_source_authorization` stable [S31]; Learn doesn't list 2026-10-01 (What's New 2026-11-07) [S30][S34].

### C5. Licensing and tenant gotchas
- **F2 (< F64): every user viewing Power BI content needs Pro, PPU or individual trial.** Free license enough for lakehouses/warehouses [S32]. [UNCERTAIN] whether API-only DAX queries count as "viewing".
- Fabric trial: 60 days, F4 or F64 sized. Only the person starting it gets a complimentary Power BI individual trial (if no PPU) [S33]. No Copilot, AI features, Private Link [S33]. [UNCERTAIN] licensing page says trial "acts like F64 for viewing" [S32]; unclear for F4-sized trial.
- SP tenant settings only needed when an SP is the caller [S10][S21]. Inference: OBO tokens are delegated, so not needed.
- Conditional Access / MFA on downstream resource: OBO returns `interaction_required` + claims challenge; return 401 with `WWW-Authenticate` so SPA re-authenticates [S1].
- Test scripts: `ActiveDirectoryPassword` deprecated, fails with MFA [S12].

### C6. Recommended flow (agent's)
1. App registrations: SPA (auth code + PKCE); API exposes `access_as_user`, pre-authorizes SPA; API delegated perms: Power BI `Dataset.Read.All`, Azure SQL `user_impersonation`, Azure AI Search `user_impersonation` ([UNCERTAIN] only community sources name the Search API, "Azure Cognitive Search"). Admin consent once.
2. SPA requests only `api://<api>/access_as_user`, calls FastAPI with it.
3. FastAPI validates `aud`, `iss`, `scp`; builds per-request `OnBehalfOfCredential` with Container App's user-assigned MI as federated credential (no secret).
4. SQL: OBO for SQL scope; mssql-python (`token_provider`) or pyodbc with pooling off. Warehouse: T-SQL RLS (`USER_NAME()` + mapping table). Lakehouse: SQL endpoint user identity mode + OneLake RLS roles bound to Entra groups.
5. Power BI: OBO for `https://analysis.windows.net/powerbi/api/.default`, executeQueries. Test users = Viewers with Build.
6. Search: push docs with `GroupIds`; app MI calls Search; user OBO token in `x-ms-query-source-authorization`. No preview: GA group-ID filter fallback.
7. Errors: OBO `interaction_required` maps to 401 + claims challenge.

### C7. Top pitfalls
1. Workspace Admin/Member/Contributor bypass Power BI RLS and most OneLake roles: test users must be Viewers [S18][S23].
2. Linux ODBC pooling can leak identities across per-user tokens [S12].
3. F2 licensing: Power BI consumers need Pro/PPU/trial [S32]. SPs can't carry RLS, so delegated path is the only per-user option [S19][S24].
